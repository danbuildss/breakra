## H. Research backlog (not approved for build)
1. **Platform hypothesis (BlockRun-style families):** contract compatibility (exists) → MCP tool-schema compatibility → code impact → release gate.
   - **What can share the engine:** JSON Schema diff and classification are reusable for MCP tool schemas (input/output schemas are JSON Schema), so it's the cheapest to try. The release gate reuses the verdict.
   - **What can't:** code impact needs a TS/JS parser; that's a separate component.
   - **What would justify expanding:** repeat users on the core plus a benchmark gap.
2. **BlockRun marketplace:** Circle lists BlockRun among platforms that help sellers list and accept x402 [web]. **Unknown:** whether it lists endpoints hosted elsewhere (Bankr) or requires its own gateway. The owner reads their seller docs; no action until then.
3. **MCP and x402 security research.** OWASP recommends pinning and reviewing MCP tool definitions; x402 terms can drift. Steps:
   1. Read the OWASP MCP cheat sheet and the x402 spec.
   2. Build a shared fixture set (10 MCP tool-definition changes, 10 x402 term changes).
   3. Run mcp-contracts and the onyx/AgentShield equivalents against it.
   4. Prototype only if a gap exists: an **offline** `breakra mcp-diff old-tools.json new-tools.json` using the existing JSON Schema rules.
   - **Stop condition:** existing tools classify the fixtures as well or better.
   - **No "Breakra Guard", no new paid endpoints.**
4. **Self-maintaining APIs (YC RFS):** a long-range frame (Detect → Impact → Resolve). Breakra's realistic role is the **Detect + verdict layer** that repair agents call. Stage 3 decides whether Impact is ours to build.
